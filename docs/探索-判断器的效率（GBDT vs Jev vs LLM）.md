# 探索：判断器的「效率」怎么比 —— 我们的 GBDT vs Jev vs LLM

> 起因：2026-09-24 晚 Ann 提「这个和 Google 的 Jev 的效率对比，可以做探索」。
> 这一份是**探索的第一天**：把事实核清、把口径定死、把**我们这边的数**量出来，并写清**唯一缺件**。
> 判据 `src/diag_judge_efficiency.py` · `scripts/fetch_jev_registry.py` · 读数 `data/judge_efficiency.json`

## 0. 先两处纠正

1. **Jev 不是 Google 的**：它是 **TypeSafe AI** 的产品（创始人 **Diogo Almeida**，ChatGPT 早期贡献者之一、RLHF 之父）。
   Google 会出现在这个话题里，是因为有人拿 **Gemini** 去做对照组。
2. **它和 LightGBM 不是同一道题**：LightGBM 吃**表**，Jev 吃**文本**。直接比「谁准」没有意义 ——
   要比的是**同一类判断任务上，不同判断器的效率口径**（见 §3）。

## 1. Jev 是什么（三类数字分开标，别混）

**① 注册表/文档事实**（可核；来源：OpenRouter 的 Jev 文档页，2026-09-24 取）：

- 模型 id **`typesafe/jev-1.13`**，别名 `~typesafe/jev-latest`；**System One** 系列的第一个。
- 输入：文本（状态对象 + 你的问题），**上下文 32,000 tokens**；**输出 token 免费**，按输入 token 计费，
  每个响应带 `usage.cost`。
- 输出：**类型化决策**，三个原语 —— **Choice**（选一个 + 每项概率 + 置信度）· **Noul**（条件是否成立 → P(yes)）·
  **Score**（有序刻度上的概率加权位置）。
- **不产出推理过程、解释或自由文本**；文档原话：它替换的是**「你问 LLM 一个窄问题、再从回答里解析出标签」这一步**。
- 接入：**一把 OpenRouter key 即可**（`POST /api/alpha/decisions` 或 `POST /api/v1/systemone`），无等待名单。

**② 第三方实测**（来源：DevelopersIO 的 107 例「文档字段突合」对照，2026-09-20；**别人量的**）：

| | Jev | Gemini 3.8 Flash（同 107 例） |
|---|---|---|
| 延迟 | **中位 ~0.7 秒/例** | 均值 1,877 ms · **中位 1,635 ms** · p95 3,380 ms |
| 成本（107 例） | **~¥0.35** | **$0.0429 ≈ ¥6.4**（输入 $0.75/M、输出+thinking $3.75/M） |
| 输出 token | **36 tok/例**（免费） | 输出 15.4 + thinking 42.4 tok/例 |
| 概率形态 | —— | **退化：semantic 64 例恰好 1.0、29 例恰好 0.0；exact 107 例全是 0/1** |
| 结论 | **速度与成本赢**；精度输给 Gemini | 精度赢；**但 5 个错例的概率是 1.0 / 1.0 / 0.95 / 0.0 / 0.2（自信地错）** |

其中一条诊断很值钱：**把输出压到十来个 token 也救不了 LLM 的速度** —— 107 例里 thinking 为 0 的 57 例，
中位延迟仍是 **1,616 ms** ⇒ **慢在"读输入到吐第一个 token"，不在生成**。

**③ 卖方说法**（**不是我们量的**，别当结论）：比普通 LLM **快 20–200 倍**、成本**低近两个数量级**、
**70–500 ms** 出结构化决策、**不会幻觉**、在 System One 类封闭任务上与 GPT-5.6 Terra 相当。

## 2. 我们这边的账（**实测**，`src/diag_judge_efficiency.py`）

| 量 | 读数 |
|---|---|
| 单条延迟 | **p50 2.011 ms · p95 2.212 ms** |
| 批量吞吐 | 5,105 行 **17.0 ms** ⇒ **29.97 万行/秒** |
| 训练（四折走查 + 早停） | **3.2 秒** |
| 边际成本 | ≈ 电费（本机 CPU，跑一万次仍是秒级） |
| **复算性** | **同输入重跑逐位一致 ✅** |
| **校准** | **29.07% 落在不确定带 [0.2,0.8]**（不是全挤两端）；**但未校准**：0.3–0.4 箱预测 34.96% / 实际 **54.31%**，0.6–0.7 箱预测 65.42% / 实际 **79.40%**（**系统性低估**） |
| 补一次校准 | isotonic（拟合在**验证折**上）：**Brier 0.1009 → 0.0957**，各箱预测均值贴上实际频率 |

## 2.5 **我们自己的 LLM 基线**（第一手，与第三方同形）

第三方那格是别人量的。我们用自己的 key 在同一批语料上补了一格（`src/diag_llm_baseline.py`）：
从 1,255 份修正公告里**分层抽 60 份**（坏→更坏 / 好→更好 / 不变 各 20），只给正文，要求回
`{"direction": ..., "confidence": 0..1}`。

| 量 | 读数（n=60，成功 60/60） |
|---|---|
| 延迟 | **p50 812 ms · p95 1,170 ms**（均值 865 ms） |
| tokens | 输入 **1,026/条** · 输出 14.8/条 |
| **与规则标签的一致率** | **51.7%** |
| **置信度** | min **0.90** · **中位 1.00** · max 1.00 · **落在 [0.2,0.8] 的比例 0.0%** |
| 判错的 29 条 | 置信度**清一色 0.90–1.00**（自信地错） |

⇒ **第三方那条结论在我们自己的语料上复现了**：**让 LLM 出概率，它给的是废概率**（中位数 1.00、没有一条落在不确定带）。
这正是 Jev 声称要填的那个市场缺口 —— 但注意下面两条边界。

⚠️ **边界（必须跟着报）**：
1. 「51.7%」是**与我的规则标签的一致率**，**不是绝对正确率** —— 标签本身来自规则抽取（更正后覆盖率 **36.1%**、人工金标一致率 **88.9%**）；
   不一致可能是模型错、也可能是我的标签错，今天**判不了**（要裁决得人工抽检一批）；
2. 这是**一个模型、一个提示、一批语料**的读数，别推广成"LLM 都这样"。
   —— 但**置信度那一格不依赖标签对错**：它在 29 条与标签不符的回答上仍报 0.90–1.00，
   而一个真正校准的判断器不会几乎处处给 1.00。

## 3. 「效率」必须拆成四条轴（**报一条都不是效率**）

| 轴 | 怎么量 | 为什么单看它会骗人 |
|---|---|---|
| **延迟** | p50 / p95（每条） | 批量吞吐好看、单条却可能慢；Jev 的 0.7 s 与我们的 2 ms 差三个数量级，但**输入形态不同** |
| **每条成本** | 每千条（含重试与解析失败） | 输出免费≠总免费；thinking 也计费（Gemini 那 107 例里 thinking 占成本 40%） |
| **复算性** | 同输入重跑一致率 | 不可复算的判断，**读数无法被别人重算** —— 那就不是可交付的读数 |
| **校准** | 不确定带占比 + 分箱 reliability + Brier | 「自信地错」比「不确定」危险得多；**阈值转人工的流程靠的就是这一格** |
| （另加）**人力** | 搭口径/判据/规则的人时 | 真正的大头，且**只有前三条全算清之后才看得见** |

## 5. 实验设计（四方 × 四轴 + 四条判据）

- **四方**：正则/关键词规则 · LLM 基线 · **Jev** · GBDT（各在自己能吃的输入上）
- **四轴**：延迟（p50/p95）· 每千条成本 · 复算性 · 校准
- **判据（四条）**：
  ① 同一批样本、同一套标签，**不许跨输入形态比准确率**；
  ② 成本要把**重试与解析失败**一起算进去；
  ③ 报**业务单位**：钱按每千条、时间按「每天要人看几条」（实测：名单每天变更**中位 2 条 / 峰值 458 条**）；
  ④ **外部数字一律标来源**（本文件里三类数字已经分开标，别在转述时把它们揉成一个）。

## 8. 场景清单：把判断器放回"时间"这件事上（六个用法）

> 来源：2026-09-24 深夜 Ann 的梦 —— 桌上一排时间戳、墙上的钟停在 18:32（而我曾在纸角写下 **21:xx**）、
> 一摞报表页脚日期层层往后挪 **365 天**、长表左列公告日右列报告期中间隔着一年、灯次第亮成一条上翘的曲线、
> 纸上多出我没写过的数字、镜子里那个 18:32 **是活的**。
> 这一节把六个用法各自**挂在一个物件上**，并给出**可量的判据**。标 ★ 的三条**不需要 OpenRouter key**就能自己先量。

| # | 梦里的物件 | 用哪个原语 | 它替代的是"我现在怎么做" | 判据（可量） | 要不要 key |
|---|---|---|---|---|---|
| 1 ★ | **墙上的钟停在 18:32** | **Noul**（时点闸） | 靠我记得「写时间前先看钟」——今晚错了两次（从记忆写 21:xx） | 每写一条带时间的句子问一次「这个时刻是从会走的钟上取的，还是从语言里取的？」；**判据 = 失败率**（本仓实测：凭记忆写时间 **2 次/天** → 装 `daily-note.mjs` 后 **0 次**） | 否（这是**代码闸**，判断器只做兜底） |
| 2 | **页脚层层往后挪 365 天** | **Choice**（两列关系） | 硬编码「公告日期 ≠ 首次披露日」这条注释 | 判「同一份数字被披露两次 / 两次不同披露 / 修订关系」；**判据 = 与茅台那条人工对照的一致率**（2016Q1：实际 `2016-04-21` vs 源 `2017-04-25`） | 是 |
| 3 ★ | **左右两列之间那道缝** | **Choice**（口径归属） | 我脑子里记着「净利润取归母、权益取含少数股东」 | 每列问一次「这列是哪个口径？」；**判据 = 与双源全量对账的一致率**（净利润：同名 **23.18%** / 对齐后 **99.60%**；权益：对含少数股东 **99.42%** / 对归母 **22.97%**） | 否（规则基线已有；判断器用来补那 **0.4%–77%** 的差额） |
| 4 ★ | **缝里往前挪、还没披露的数字** | **Score**（有序刻度） | 我的正则：**36.1%** 覆盖、人工金标一致 **88.9%** | 把修订判成"更坏 / 不变 / 更好"的**概率加权位置**；**判据 = 与 1,255 份既有方向标签的一致率 + 不确定带占比**（LLM 基线已有：一致率 **51.7%**、不确定带 **0.0%**） | 否（基线已量；判断器那格要 key） |
| 5 ★ | **次第亮起、亮成一条上翘曲线的那排灯** | **Noul**（PIT 闸门） | 我漏过一次，靠两套实现对账（差 1 条）才发现 | 每条事件问「它是否**晚于**该公司的骨架可用日？」；**判据 = 被闸住的条数**（实测 2024 丢 **228** 条 / 2023 丢 **268** 条）+ **跨实现对账是否仍一致** | 否（**必须是代码闸**：判断器再快也不该替这个位置） |
| 6 | **门外那个念到一半就散掉的名字** | **Choice**（发布前红线门） | 正则查字面；它会漏指代、也会把**引用的规则条文**读成事实 | 问「这段文字里有没有不该落纸的实体 / 这句是本案原因还是引用规则？」；**判据 = 发布前扫描的命中数**（本仓实测：个人面 **0 命中**；原因归类锚点覆盖 **67.5%**、① 组 45 条只读量级） | 是 |

**两条从这张表里长出来的结论：**

1. **六个用法里，只有三个真的需要判断器**（2 / 6 / 以及 4 的"判断器那一半"）——
   另外三个（**1 时点闸 · 3 口径归属 · 5 PIT 闸门**）**更适合写成代码闸**：
   它们要的是"每次都跑一遍"的确定性，而**判断器给的是概率**。**把确定性的事交给概率装置，就是给自己造一个新的不确定源。**
2. **判断器的价值集中在"语义 vs 字面"这条缝上**：正则看得见字面（查得出那三个字），看不见指代与引用；
   而这条缝的宽度我们量得到 —— 锚点覆盖 **67.5%**（剩下 32.5% 要人看）、同名不同物 **23.18% vs 99.60%**。

⚠️ **前置条件（决定上面几条能不能成立）**：判断器的概率必须真的**摊得开**。
自家 LLM 基线：置信度**中位 1.00**、不确定带 **0.0%**、判错的 29 条置信度清一色 0.90–1.00；
GBDT：不确定带 **29.07%**、补一次 isotonic 后 Brier **0.1009 → 0.0957**。
⇒ **若 Jev 的概率长成 LLM 那样，第 2/4/6 条里靠阈值转人工的部分当场作废**。
**拿到 key 之后第一个该量的不是准确率，是这一格。**

## 9. 对照台（可跑）：只收"语义"任务，只留一个 call hook

`src/judge_arena.py` —— 把 §8 里**真的需要判断器**的那几条做成考卷（**算术能判的一律不收**）：

| 任务 | 原语 | 题量 | 题面 | 真值来源 | 基线 |
|---|---|---|---|---|---|
| **rev_dir**（修订方向） | **Score**（0–4 有序刻度） | 120（坏 50 / 不变 35 / 好 35） | 相比前次预告改好还是改坏？ | 规则标签（1,255 份；人工金标一致 **88.9%**） | 规则：覆盖 **36.1%** · LLM：一致 **51.7%**、不确定带 **0.0%** |
| **st_reason**（戴帽原因） | **Choice**（A/B/C/D） | 120（合规 53 / 财务 41 / 未归类 19 / 重整 7） | 触发戴帽的原因属于哪一类？ | 规则标签（211 份；锚点覆盖 **67.5%**） | 规则：锚点覆盖 **67.5%** |

**三条设计约束（都是踩出来的）**：
1. **D=说不清也是一个合法答案** —— 规则的 32.5% 抽不到，就该让判断器**把"说不出"说出来**，
   而不是逼它在 A/B/C 里猜（这正是"规则条文被读成事实"那类错的入口）；
2. **`--judge openrouter` 缺 key 时大声停住**，不做静默降级 —— 否则会拿规则基线冒充判断器的数；
3. **题面/金标模板不入库**（含公告正文摘录）⇒ 一条命令可重建：`python src/judge_arena.py --dry --gold 60`。

**`--gold 60` 导出的人工裁定表才是真值升级口**：现在的真值全是**我的规则标签**，
不补一层人工金标，一切对比都只是"与我的规则有多一致"（这句话要一直跟着读数走）。

```bash
python src/judge_arena.py --dry --gold 60        # 建题 + 规则基线 + 打印一例 Jev 请求体（不联网）
python src/judge_arena.py --judge openrouter     # 有 key 时：把 Jev 那一格插进去（缺 key 明确报错）
```

## 10. 金标第一跑（2026-09-25 凌晨）：**它先照出的是我的标签，不是模型**

两件事同一天做完：`src/make_gold_review.py`（生成精简复核册）+ 两个独立读者逐条裁定。

| 任务 | 谁读 | n | 判不了 | 与规则标签一致率 | 不一致集中在 |
|---|---|---|---|---|---|
| **rev_dir** | 我（逐条读摘录，写刻度 + 理由） | 30 | **0** | **88.9%（16/18）** | **邻近科目被当净利**（营收/净资产，2 条） |
| **st_reason** | 另一个窗口独立读（各条留理由），**三轮：窗口·只往后 → 切样板段+锚点前后 → 整篇全文** | 60 | **11.7% → 5.0% → 0%** | **73.6%（39/53）→ 77.2%（44/57）→ 75.0%（45/60）** | 规则没覆盖到（规则=D）6 · 真分歧候选 7 · 规则没有 E 档 2 |

⚠️ 一致率**不是单调上升**：v4 把最后 3 条从"判不了"变成判得出（`000677`→A 与规则一致、`600165`/`688089`→E 规则没有这一档），
⇒ 分母也变了（53 → 57 → 60）。**比"一致率"要连着分母一起读**；这条读数真正单调的是**判不了率**：**11.7% → 5.0% → 0%**。

**复核册本身也要量（第二跑加的）**：同一批 60 条、只把摘录改好（先切掉「拟采取的措施」这类样板段 +
锚点前后各取一段），**两版都可判的 52 条里只有 80.8% 一致** —— 13 条从"判不了"变成"判得出"、1 条回归、2 条多值主值变化。
⇒ **判不了率与裁定都不是摘录的"无关项"**：扩 n 之前先修册子，否则扩的是噪声（这条读数是"先修册子"这个决定的依据）。

**册子四修（每一步都留在这儿，因为每一次都是被一个具体的错推着走的）**：

| 版本 | 取法 | 它踩到的坑 |
|---|---|---|
| v1 | 从**第一个**命中词起取 360 字 | 7/60 落在「董事会拟采取的措施」样板段；5 条把「…意见的审计报告」的**主语切在切口另一侧**（而「内控 vs 财务报表」正是 A/B 分界） |

⚠️ **一处我说错并当场改掉的归因**：我在 v3 那一行原写「这批 PDF 抽出的文本**不全按阅读顺序**」——
那是**从一个 200 字的窥视里推断的**（我只看了 660 字窗口的头 200 字就下了结论）。
独立读者把 60 条正文全文重建后实测：**触发原因全部落在前 900 字内**（只有 1 条的判据文字在 1,290 字处、而它的数字在前），
⇒ 三条的差异**应归因于窗口边界**，不是文本乱序。**「我看了 200 字就推断了一篇文档的排版」= 又一次拿截断视图当全文。**

⚠️ **同一次里第二个"说法 ≠ 实物"**：v4 的第一版实现里，`st_excerpt()` 的 docstring 写着「整篇 [:3000]」，
而外层又套了一次 `[:900]` ⇒ 60 条**每条恰好 900 字**（是独立读者按 900 字整整齐齐发现的）。
现已删掉外层那一刀，并把「是不是整篇」变成**生成后当场量的读数**（见上表 v4 行的三个数）——
**声明与实物必须同一次核对**，这次是别人替我核的。

**两个被独立读者点名的口径边界（已定，写在这儿免得下次再问）**：
1. **B 的边界**：「连续三年扣非孰低为负 + 最近一年审计报告显示持续经营存在不确定性」（深 9.8.1(六)/(七)）**算 B**（它性质是财务、A/C/E 都不沾）——已写进选项文字。
2. **多值取哪一条**：公告同时写「背景触发」与「本次叠加的触发」时，**取正文中较早出现的那个**（`002717` 是唯一一条两种读法给出不同字母的：位置规则 ⇒ B，本次触发 ⇒ A）。已写进选项文字，让裁判与金标同一条规则。

⇒ 一句可搬走的教训：**文本短的时候，最小风险的取法是"别挑"** —— 挑错的代价高于多给几百字的代价。
**口径也补了一档**：`E = 生产经营类`（「生产经营活动受到严重影响且预计 3 个月内不能恢复」）——
这不是我编的档，它是交易所规则里**与内控意见、财务指标并列的第三条触发**，实测 `600165`（子公司临时停产）· `688089` 两条原本被硬塞在 A/B/C 之外判不了。

**rev_dir 这一跑直接改掉了分类器**（不是改结论的语气，是改数）：
- 第一跑只有 **56.7%** 一致，13 条不一致里 **12 条是分类器说「不变」而公告明显改了**；
- 根因：切不到「修正后的预计业绩」那一行时，前后两段**退化成同一段** ⇒ 抽出的区间逐字相同 ⇒ 必然「不变」；
- 修后（`src/classify_yjyg_rev_dir.py` 加四道闸）：覆盖 **48.4% → 36.1%**、**「不变」这一类本方法判不了**、翻面率 **20.1% → 26.5%**、
  下修:上修 **1.7:1 → 1.75:1**（结论稳，比例没塌）。详见 [`设计-业绩预告滚动链.md`](设计-业绩预告滚动链.md) §7.1.1。

**这一步证明了一件事（也是它值得做的理由）**：金标的价值不在"给模型打分"，
而在**它先给标签打分** —— 一个 1,855 份文本的语料上，我的规则标签本来就带着一整类系统性伪影，
而它一直是后面所有读数（包括我今晚报出去的"下修上修比"）的地基。

⚠️ **两条跟着走的边界**：① 两个"独立读者"里有一个是另一个 LLM（不是人）⇒ 73.6% 是**两个自动读者的分歧率**这次尤其要小心解释；
② 摘录本身有缺陷（ST 那批的锚点常落在样板段 ⇒ 11.7% 判不了），**先把复核册修好再扩大 n**，否则扩的是噪声。

## 11. 第一个真第三方判断器跑完 120 道（2026-09-25 凌晨）—— `glm-5.3` @ OpenCode

**怎么跑起来的**：不是 Jev，而是**她自己的 OpenCode key**。实测把两件事分清了：
① `/zen/go/v1`（**Go 订阅**那侧）**必须带 `x-opencode-session` 头**（缺了 400 `MissingSessionID`）—— 真坑；
② `jev-1.13` **只在 `/zen/v1`（按量付费）那侧**，而那一侧对她账号先是 **402（没钱）**、充值后变成 **503 `Endpoint is unavailable`**
（同一时刻 `deepseek-v4-pro` / `glm-5.3` 都是 200，`claude-sonnet-5` / `gpt-5.5` 与 jev **一起** 503 ⇒ **是 OpenCode 侧那几个上游不可用，不是钱、不是 key**）。
⇒ 于是**不等 Jev**：用 Go 通道的 `glm-5.3` 先把考卷跑完。命令就一条：
`python src/judge_arena.py --judge opencode --model glm-5.3 --task st_reason`。

### 11.1 四轴读数卡（两跑合成：主跑 + 补跑）

| 轴 | 读数 | 备注 |

### 11.2 它答不出的 11 条，两种形状（都记下来，不合并）

- **7 条撞满 6000 token 上限**（HTTP 200、`completion_tokens=6000`、正文空 —— 一直在想，想不完）；

### 11.3 它判错的 2 条，与我规则的错**是同一对邻居**

`600370`（真值 B，判 A）· `002528`（真值 B，判 A+另:B → 主值 A）。
两条都落在 **「内控审计意见 ⇒ A」vs「财务报表审计意见 ⇒ B」** 这条缝上 —— 而**我的关键词规则最常犯的错也是这一对**（5 条，方向相同）。
⇒ 这支持一个比"谁不行"有用的结论：**那对边界是任务本身的难点**（公告模板把两条意见并列、且常把财报那句排在前面），
不是某一方特别笨。**判断器的价值正是在这种缝上，但它也没有把这条缝完全填平。**

### 11.4 校准（第三次同形状；**但被下一节的 kimi-k3 反证了一半 —— 见 11.7**）

置信度**中位 0.980**、不确定带 **[0.2,0.8] 占比 0.00%**、Brier(置信度 vs 是否答对) **0.1377**（两处错都给了 0.9）。
三家（自家 DeepSeek 基线 / 这份 glm-5.3 / 文献里的生成式 LLM）**全部概率饱和**。
⚠️ **2026-09-25 07:5x 更正**：同一个早晨换了一个模型家族（`kimi-k3`，见 11.7）⇒ 它**有 4.17% 落在不确定带里**（120 条里 5 条），且**它判错的两条低置信样本（conf 0.72）正在其中**。
⇒ 正确的说法不是「LLM 的概率必然饱和」，而是「**我测过的四家里三家饱和、一家能摊开一点点**」——**能不能摊开是具体模型的属性，不是这一类的宿命**（这条更正直接改掉了「这类不能用」的推论范围）。
⇒ 落地含义不变且更硬：**这一类判断器不能用于「低置信自动转人工」**——它不会告诉你它什么时候不确定；
要那条路，得用概率真的摊得开的那一类（我们这边 GBDT：不确定带 **29.07%**，isotonic 后 Brier 0.1009→0.0957）。

### 11.5 过程中抓到我自己的一处尺子错（**它差点造成一个假读数**）

第一版审计脚本里我写了 `.str[:1]` 想"取首字母"，结果把模型输出的 **`"A+另:B"` 读成"答对了 A"** ——
3 条本来"没答成单字母"的样本被算进"可判"，读数从 20 条弃答变成"只有 17 条没答"，还让一致率看起来更漂亮。
**那是尺子造的，不是模型答的。** 已改成显式解析（`_primary()`：主值 = 首字母，其余 = 多值标注），
并把这条禁令写进函数注释。⇒ 同族于今晚早些时候那条：**报读数之前先问"这个数是量出来的还是我算出来的"**。

### 11.7 换一个模型家族：`kimi-k3` vs `glm-5.3`（同一套 120 道题）—— **答案不是"差不多"**

| 轴 | `glm-5.3` | **`kimi-k3`** |
|---|---|---|
| **覆盖率** | 109/120（90.8%） | **120/120（100%）** |
| **一致率（答出的）** | **98.2%**（107/109） | 95.8%（115/120） |
| **一致率（空算错）** | 89.2% | **95.8%** |
| 延迟中位 | 7,554 ms | **2,986 ms** |
| 延迟 p95 | 71,911 ms | **10,951 ms** |
| completion tokens（120 道合计） | 102,491 | **31,858** |
| 置信度中位 | 0.980 | 0.980 |
| **落在不确定带 [0.2,0.8]** | **0.00%** | **4.17%** |
| 多值标注率 | 4.2% | 3.3% |

**三件从这张表里读出来的事**（都不是"谁更强"）：

1. **两家的失败形态完全不同**：glm 的 13 条"错"里 **11 条是它答不出/答不完**（撞 token、网络），真判错只有 2 条；
   kimi **一次也没答不出**，5 条全是真判错。⇒ **同一张卷子，一个败在"说不完"，一个败在"说错"**；
   只看一致率会把这两种完全不同的毛病读成同一个数（0.982 vs 0.958）。
2. **两个模型彼此一致 90.0%（108/120）**，而且 **kimi 的 5 条错，glm 全都错**（重合 5/5）；
   glm 那 8 条"独有错"里没有一条是 kimi 答对的 − kimi 答对的那部分两人一致。
   ⇒ **重合的这 5 条（`002528`·`300125`·`300225`·`600745`·`603557`）是"任务难点"的候选**：
   其中 4 条是 gold=B 而两家都答 A（**内控意见 vs 财报意见那条缝**），第 5 条（`300125`）kimi 给的是 `E+另:A,B`、
   conf **0.72**（它自己也不确定，而且落在不确定带里 —— 全批 5 条不确定样本之一）。
3. **延迟与 token 消耗差 2.5–3 倍**（3.0 s vs 7.6 s；32k vs 102k completion tokens）⇒ **延迟不是"这一类的固有属性"，是按模型可选的**；
   配上"两家的错高度重合"，工程含义很直接：**选便宜快的那家，错误集合几乎不变**（在这张卷子上）。

⚠️ **边界**：① 这条只跑了 ST 这一类题（120 道），**没跑 rev_dir**；② 两家都是**自动读者**的裁决真值当裁判（与我的规则标签一致 71.7%）；

④ 成本仍**未量**（Go 套餐内无逐次计费字段记录；只有 token 数是真的）。
