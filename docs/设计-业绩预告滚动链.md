# 候选设计：业绩预告 → 滚动更新链路

> 现状：预告只做到"披露链多一格"（在它那一刻加一列特征，跑出 0.9987/0.9985）。
> **没做成的是"能上线的形状"**：事件驱动的入库、名单变更、可追溯、以及它自己的一套判据。这份是最小设计。
> 判据 `src/analyze_yjyg_rolling.py` · 读数 `data/yjyg_rolling.json`。

## 0. 先把话说清楚：这一格的分不是模型的本事

| 决策时刻 | 子集 | n | 正例率 | AUC | top-10% 命中 |
|---|---|---|---|---|---|
| 业绩预告公布后 | **有预告的样本** | 10,476 | 44.11% | **0.9985** | **99.90%** |
| （对照）一季报披露 | 全体 | 19,473 | 23.91% | 0.9103 | 84.95% |

**AUC 0.9985 的意思是"输入里写着答案"**：预告原文就是公司自己对全年业绩的预告，
`预告类型` 与最终"是否亏损"几乎一一对应（见 §2）。所以——

> **这一格真正值钱的不是分，是两样东西：提前量（中位 86 天）与覆盖（会亏的公司 99.25% 会发预告）。**

**它不是"偷看"**：预告是**真实公开披露**，发生在决策时刻之后，用它完全合法 ——
这跟 B 臂（在半年报还没披露时就把它的数字接进特征）性质完全不同。**区别在"信息公开的时点"，不在"有没有用"**。

## 1. 覆盖：谁会有预告（正负两边都要看）

| 组 | 有业绩预告的比例 | n |
|---|---|---|
| **真会亏**的公司 | **99.25%** | 4,656 |
| 不亏的公司 | 39.52% | 14,817 |
| 全体 | 53.80% | 19,473 |

⇒ 预告对"会亏"的公司**近乎全覆盖**（这就是它能当"确认通道"的原因）；
对"不会亏"的公司只有四成，**所以它不能用来扩容名单**（名单骨架仍要靠定期报告链）。

## 2. 内容：预告类型几乎等于答案

| 预告类型 | 最终真亏 | 最终不亏 |
|---|---|---|
| 首亏 | **1,921** | 5 |
| 增亏 | **1,095** | 1 |
| 续亏 | **328** | 0 |
| 减亏 | **1,242** | 3 |
| 扭亏 | 12 | 1,190 |
| 预增 | 0 | **2,294** |
| 预减 | 15 | 1,720 |
| 略增 / 略减 / 续盈 / 不确定 | 1 | 638 |

聚合口径：预告里**预计亏损（预测数值 < 0）**的 4,597 条，最终真亏 **99.78%**；
**预计不亏**的 5,879 条，最终真亏 **0.58%**（这 0.58% 就是这一格的**上界噪声**）。

## 3. 时点：它买到的提前量

| 量 | 值 |
|---|---|
| 预告公告日 → 年报披露日 | P5 **49** 天 · P25 75 · **中位 86 天** · P75 91 · P95 100 |
| 预告公告日 → 上一个定期报告（三季报） | 中位 **275 天** |
| 预告日期晚于年报的条数 | **0 条**（干净；对比业绩快报那一格 67.8% 为负 ⇒ 那格做不了） |

⇒ **滚动链的定位**：在"三季报（10 月）"与"年报（次年 4 月）"之间那条 6 个月的空档里，
**用一条真实公告把名单从"预测"升级为"已知"**。

## 4. 最小设计

**① 触发点**：业绩预告公告日（每年 1 月–4 月，中位落在年报前 86 天）。
**② 更新频率**：**事件驱动**，不是周期批跑 —— 收到公告即更新那一家。
**③ 与定期报告链的关系**：

```
一季报(4月) ──► 半年报(8月) ──► 三季报(10月) ──┬──► 预告滚动(次年1–4月，事件驱动) ──► 年报(4月)
  名单骨架              ← 定期报告链负责 →        └── 名单变更：把"预测"升级为"已明说"
```

**④ 判据（每条都要有一条不依赖人当裁判的检查）**：
1. **必须用公告日入库**，不许用"更新日"—— 数据源的日期字段会晚 365 天，这条已经在别处量过（`docs/口径.md`）；
2. **覆盖自检**：每个财报季，"会亏样本里有预告"的比例应稳定在 **≈99%**（掉下来 = 抓取漏了，不是市场变了）；
3. **可追溯**：每一次名单变更都能指回**哪一条公告**（本线已有 `data/st_reasons.csv` 那种"每条事件留证据"的形状）；
4. **修订不改历史**：同一家公司后来的修订版**另存一条**，不许覆盖已入库的那条（否则回测里会偷偷用上未来信息）；
   **修订的检测口必须在公告源**（见 §7 —— 东财表根本不返回修订前那一版）；
5. **一致性上界**：预告"预计亏损"但最终不亏的比例应 ≈**0.58%** 量级；若显著偏离，先怀疑抓取而不是市场。

## 5. 边界与"做不了"

- ⚠️ **它不能扩容名单**：不亏的公司只有 39.52% 有预告（见 §1）；
- ❌ **业绩快报那一格仍然做不了**：它的"公告日期"被"下一年再披露"污染（与年报日相减 67.8% 为负），
  **默认不纳入**（预告干净，快报不干净 —— 这两格必须分开说）；
- ⚠️ 0.9985 是**在有预告的子集上**读的，**不能与全体的 0.9103 并列**成"提升"；
- ⚠️ §1 的"提前量中位 86 天"用的是**归母净利润那一行的公告日**；约 **1.87%** 的公司**分指标披露**
  （先发营业收入、后发净利润，见 §7）⇒ 对这些公司，按"第一条预告"触发会**早于净利润出现**，触发口要写成"含归母净利润的那条公告"。

## 7. 「修订」这一格量到底了：**市场有修订，这个数据源看不到**

**先纠一个词**：原始文件里每家公司有多行（平均 2.29 行/公司·年），**但那是同一天披露的多个指标，不是多版本**。
判据是**按公司看不同的公告日期个数**（`src/diag_yjyg_versions.py`，覆盖 2015–2026 · 64,715 行 · 28,316 公司·年）：

| 量 | 实测 |
|---|---|
| 只有一个公告日期的 | **98.13%** |
| ≥2 个公告日期的 | **1.87%**（530 个公司·年），两次间隔中位 **74 天** |
| 这些"多日期"是什么 | **分指标披露**，不是修订。例：`000010` 2022 年度 —— **2023-01-30** 发营业收入/扣除后营业收入（预减），**2023-04-22** 才发归母净利润（首亏 −5.5 亿）、扣非、每股收益 |
| 多版本里主口径（归母净利润）两端都有的 511 个 | **数值变了 0.00% · 预告类型变了 0.00% · 盈亏翻面 0 个** |

**再看另一头（公告源）**：用巨潮检索「业绩预告修正」（`stock_zh_a_disclosure_report_cninfo`）把 **2015–2026 全部拉下来**
（`scripts/fetch_yjyg_revisions.py`，按年切、可断点续跑）——**3,306 条**修正公告：

| 报告期 | 条数 |
|---|---|
| **年度** | **1,571** |
| 半年度 | 906 |
| 季度 | 587 |
| 未标 | 242 |

**年度修正公告逐年**（按发布年）：2015 **147** → 2018 **210** → **2019 282（峰值）** → 2022 78 → 2024 69 → 2025 45。
（⇒ 修订**在变少**，但仍年年有；`2016 会计年度 175 条 … 2024 年 45 条`。）

**修订发生时点（这是触发口的实测依据）**：与面板对得上 **1,108/1,571 = 70.5%**（对不上的多在 2016 前或已退市），
这批修正日 → 年报披露日：

| 量 | 值 |
|---|---|
| 提前量 | P5 **2** · P25 **14** · **中位 62 天** · P75 85 · P95 98 |
| **发生在年报披露之前的** | **97.47%**（其余 2.53% 是年报当天/之后 ⇒ 那部分**不能当预告用**） |
| 月份分布 | **1 月 620** · 2 月 81 · 3 月 72 · **4 月 311** · 其他 24 |

⇒ **双峰**：一波在**一月**（提前两个月就把坏消息改成更坏），一波在**四月**（年报前夜紧急下修）。
⇒ **触发口的设计据此确定**：**每日轮询公告源**（不是读东财表），命中「年度业绩预告修正」即触发那一家重算；
**过滤条件 = 修正日必须早于该公司的年报披露日**（那 2.53% 要丢掉）。

> **⇒ 结论**：**修订是真实存在的**（2015–2026 共 **1,571 条年度修正**），而 **东财那张表只返回一条、且是修订后那一版**
> —— 所以"0 个翻面"量的是**数据源的形状，不是市场的形状**。
> ⇒ **滚动链的触发口与修订检测必须走公告源（巨潮），不能走东财表**；本线已有的公告检索/取证链路（ST 那条）可以直接复用。

### 7.2 回放：这条链**真的走了一遍**（`src/rolling_replay.py`）

不是再跑一遍模型，而是给定日期 D、只喂 D 之前能看到的东西，输出**当天名单 + 每一条变更的理由**。
骨架＝① 一季报那一刻的分数（前 10%），事件＝业绩预告 + 修正公告。

| 会计年度 | 名单 | 事件（PIT 闸门后） | 名单内被公告兑现/解除 | 拆开看 |
|---|---|---|---|---|
| **2024** | 503 只 | 2,897 → **2,669**（丢 228） | **482 只（95.8%）** | 明说会亏 **432** · 误报解除 **37** · 修订 **13** · 未确认 21 |
| **2023** | 483 只 | 2,959 → **2,691**（丢 268） | **465 只（96.3%）** | 明说会亏 **370** · 误报解除 **81** · 修订 **14** · 未确认 18 |

**判据**：**2,630 / 2,629 条状态变更，100% 可溯源到一条公告**（每条带日期 + 标题，`orphan = 0`）。
⇒ 滚动链的产品价值被量成两句话：**名单里 96% 的公司会被公告明确兑现或解除**，
而**解除率（2024 年 7.4%、2023 年 16.8%）就是这张名单的"误报浮出水面"速度**。

⚠️ **回放当场抓出的两个自己犯的错**（都留在这儿防复发）：
1. **PIT 闸门**：第一版从事件最早的一天就开始应用，而名单要到**该年一季报披露后**才算得出来 ⇒
   **在自己的回放里犯了本项目要治的错**（2024-01 的事件用上了 2024-04 的名单）。修法：**一条事件只有在"该公司的骨架分数已存在"之后才允许应用**（2024 丢 228 条、2023 丢 268 条）。
2. **跨源日期陷阱**：东财表里**有过修订的公司**，其"公告日期"是**最后一次披露日** ⇒ 会排在修正公告**之后**（例 `002173`：预告日期 2025-02-26，而修正更早）。
   修法：这些公司的预告事件**标成"日期存疑"、不参与建立"修订前"状态**，只让修正说话。

### 7.3 日更循环：一天一天走，落一份可回看的**变更台账**（`src/rolling_daily.py`）

`rolling_replay.py` 是**一次性走完**（给窗口、出总账）；`rolling_daily.py` 是**按日推进**（读当天新公告 → 更新状态 → 输出当日 diff），
两者**共用同一套骨架、PIT 闸门与事件口径** ⇒ **总数必须对得上，这就是自检**。

| 会计年度 | 名单 | 变更总账 | 名单内 | 有变更的天数 | 每天要人看的量 | 名单状态推进 |
|---|---|---|---|---|---|---|
| **2024** | 503 | **2,630** | 482 | **70 天** | 中位 **2 条/天** · 峰值 **458**（2025-01-18）· 名单内 ≤**117**/天 | 明说会亏 0 → **432** · 未确认 503 → **21** |
| **2023** | 483 | **2,629** | 465 | **101 天** | 中位 **1 条/天** · 峰值 **981**（2024-01-31）· 名单内 ≤**238**/天 | 明说会亏 0 → **370** · 未确认 483 → **18** |

**台账形状**（`data/rolling_daily_<year>_ledger.csv`）：`日期 · 代码 · 从状态 · 到状态 · 公告类型 · 公告标题 · 在不在名单 · 分数 · 是否首次确认`
—— **每一次名单变化都能指回"哪一天、因为哪一条公告、从什么状态到什么状态"**。

**逐日曲线**（`data/rolling_daily_<year>_days.csv`）：每天的变更数 + 名单里"已明说会亏 / 已确认 / 未确认"的累计数
⇒ 它就是上线后**监控面板**该画的三条线。

⚠️ **自检当场抓出一个不一致（已修）**：日更版第一次跑 2023 得 **2,630**，而一次性回放是 **2,629** —— 差 1 条。
根因：一次性回放有**右端截断**（年报披露最晚日之后的事件不改名单），而日更版第一版没有。
修法：日更版也截到年报最晚披露日（2023 丢 1 条、2024 丢 0 条），两版**对上**（2629/2629、2630/2630）。
⇒ **两套独立实现的对账，比任何单侧自查都管用**（差 1 条也能问出"哪一套少了一道闸"）。

### 7.1 修订的**方向**（读正文，两个独立读数交叉验证）

标题不含数字 ⇒ 拉 **1,255 份修正公告 PDF 正文**（`scripts/fetch_yjyg_rev_pdfs.py`，成功 1,255/1,256，正文中位 1,225 字），
用两种**互相独立**的读法各读一遍（`src/classify_yjyg_rev_dir.py`）：

| 读法 | 结果 |
|---|---|
| ① 数值对比（只在含「归属…净利润」的行里取**区间**，前段 vs 后段） | 覆盖率 **48.4%**（607/1,255）：**坏→更坏 291 · 好→更好 168 · 不变 148**；**盈亏翻面 122 条（20.1%）** |
| ② 勾选框（正文里的 `亏损 / 扭亏为盈 / 同向上升 / 同向下降`） | 亏损 **220** · 同向上升 163 · 扭亏为盈 **159** · 同向下降 33 · 其他 2 · 读不到 678 |
| **两读法交叉一致率** | **98.7%**（只有 8 条"数值翻面但勾了同向*"，多为区间跨零的边界样本） |

**两个数字值得记住**：
- **下修 : 上修 ≈ 291 : 168 ≈ 1.7 : 1** —— 修订**倾向于报坏消息**，这与"预告这格几乎等于答案"叠加后，
  意味着**修订事件本身就是一条负向信号**，滚动链应当给它更高的优先级；
- **约 20% 的修订是盈亏翻面**（122 条）—— 这是"名单从预测变已知"里**信息量最大的那一类**。

⚠️ **v1 的教训（写在这里防复发）**：第一版在整段里"取所有数字求平均"，把**不同科目**（营业收入/扣非/每股收益）混进来，
抽出的前后对比有假样本（例：`-3,900万 → 10,319万`，而两段文本都写着 20000）。
⇒ v2 改成**只在含「归属…净利润」的行里取区间**，覆盖率从 75.5% 降到 48.4% —— **降下来的是可信度换来的**；
并用勾选框做第二个独立读数交叉验证（98.7% 一致）。**宁可覆盖率低，也不报一个抽错的数。**

## 8. 复跑

```bash
python scripts/fetch_yjyg_revisions.py     # 巨潮「业绩预告修正」清单，按年切、可断点续跑 → data/raw/yjyg_rev/
python src/diag_yjyg_revisions.py          # 年度修正事件表 + 提前量分布 → data/yjyg_revisions.json
python scripts/fetch_yjyg_rev_pdfs.py      # 1,255 份修正公告正文（可断点续跑）→ data/raw/yjyg_rev_pdf/
python src/classify_yjyg_rev_dir.py        # 修订方向（数值对比 × 勾选框，双读数交叉）→ data/yjyg_rev_direction.json
python src/rolling_replay.py --year 2024   # ★ 离线回放：名单 + 每条变更的理由（判据：可溯源）
python src/rolling_daily.py --year 2024    # ★ 日更循环：逐日 diff + 变更台账（自检：与回放对账）
python src/analyze_yjyg_rolling.py         # 覆盖 / 时点 / 内容 / 上界 → data/yjyg_rolling.json
python src/diag_yjyg_versions.py           # 多版本 vs 多指标 / 翻面率 → data/yjyg_versions.json
```
